# Backend Plan — Resolve AI

Status: **Draft, pending approval**
Scope source: *Resolve AI — New Foundation* (product source of truth). The route list and team conventions come from the *Revised PRD v2*.

## 1. What the backend implements

**Detect → Understand → Recommend → Act → Measure → Report**, for **data-bundle engagement** (MVP use case), on synthetic data.

| Step | What happens | Who decides |
|---|---|---|
| 1. **Detect** | Compare each customer's recent bundle activity with their own baseline; flag meaningful changes; assign a disengagement priority | Deterministic analytics |
| 2. **Understand** | Find the likely reason. Use behavioral **evidence** when it exists (for example, failed activations → `activation_difficulty`). When it doesn't, create a **feedback request** that is handed off to one of **Orange's existing channels** (SMS, call, …). **Orange's channel contacts the customer**; Resolve AI only ingests the reply. AI turns informal replies into a formal reason code, confidence, sentiment and summary | Rules for evidence; AI for text; human can override |
| 3. **Recommend** | Choose the next-best action from **the change + the reason**, with why, objective and confidence | Deterministic rules |
| 4. **Act** | An Orange team member approves or rejects; approval creates an intervention that is handed off to **Orange's existing workflows** to execute; Resolve AI records it | Human |
| 5. **Measure** | After the intervention window, recompute activity and compare with pre-intervention behavior | Deterministic analytics |
| 6. **Report** | Signals, priorities, reasons, feedback coverage, actions, outcomes, drivers, trends | Deterministic queries; AI may summarize |

> *We noticed something changed. We don't want to guess why. We use evidence, ask the customer when information is missing, understand the response with AI, recommend the appropriate action, and measure what happened next.*

**Demo journey: Customer LR-20417**

> Normally activates 18 bundles/month, only 6 this month (**−67%**) → detected, high priority → no behavioral evidence of a cause → feedback request handed off to Orange's SMS channel → Orange's channel collects the reply *"Money hard this month. Buy small weekly."* → Resolve AI ingests it → AI: `affordability`, confidence 0.86, negative sentiment → recommend an eligible lower-cost bundle → manager approves → handed off to Orange to execute → 30 days simulated → measured: activations recovered → appears in the report.

## 2. Guiding rules

1. **The LLM is never the source of truth.** Metrics, priorities, recommendations and outcomes are deterministic. The LLM only (a) classifies free text into a fixed reason code and (b) phrases summaries of structured facts.
2. **Fixed reason taxonomy** (6 codes, matching the frontend) with `unknown`. Low confidence → `needs_review`.
3. **AI is optional at runtime.** If OpenRouter fails or times out, a keyword classifier takes over and the result is marked `keyword_fallback`.
4. **Resolve AI never contacts customers.** It decides *who* needs feedback and *why*, then hands the request to Orange's existing channel, which does the outreach. Requests are only suggested for prioritized customers whose reason is unknown, not for every customer.
5. **Human in the loop.** Nothing is handed off for execution without an approval record.
6. **Honest labelling.** The score is a *disengagement priority* (`model_version: "rules-v1"`), not churn prediction. Channel replies, public comments and post-intervention behavior are marked `simulated`.
7. **Two currencies.** Orange Liberia sells bundles in **USD and LRD**. Amounts are stored in their original currency. Analytics compare spend in a USD-equivalent using a configured exchange rate, and reports show both.
8. **Contract first.** Each feature documents its endpoints in `docs/api-contract.md` so the frontend can build in parallel.

## 3. Stack

| Concern | Choice |
|---|---|
| Runtime | Node.js 22 LTS + TypeScript (strict) |
| HTTP | Express 5 |
| Database | PostgreSQL on **Neon** (hosted) |
| ORM / migrations | Drizzle ORM + drizzle-kit (migrations committed) |
| Validation | Zod (env, params, bodies, LLM output) |
| Logging | Small `lib/logger.ts` wrapper over `console` |
| AI gateway | OpenRouter behind an `LlmProvider` interface + keyword fallback |
| Code quality | ESLint + Prettier, `tsc --noEmit` |

**Deferred:** automated tests (Vitest/Supertest) and pino. Each PR includes manual `curl` test steps instead.

## 4. Project structure

```
backend/
  src/
    app.ts                 # builds the Express app
    server.ts              # starts the HTTP server
    config/env.ts          # Zod-validated environment
    config/rules.ts        # windows, weights, thresholds, reason → action map: one place to tune
    db/
      client.ts
      schema/              # one file per table
      migrations/          # generated by drizzle-kit
      seed/                # catalog, customers, activity, scenarios, feedback text library
    modules/
      customers/  detect/  understand/  recommend/  act/  measure/  report/
      ai/                  # LlmProvider, OpenRouter, keyword fallback
      copilot/
      simulation/          # demo-only: channel replies, post-intervention activity
    middleware/            # error handler, validate, not found
    lib/                   # http errors, logger, pagination
```

Each module: `*.routes.ts` (HTTP only) → `*.service.ts` (logic) → `*.repository.ts` (Drizzle).

## 5. API conventions

- Base path `/api/v1`, plural nouns, kebab-case paths, camelCase JSON.
- Success: `{ "data": ..., "meta": { "page", "pageSize", "total" } }` (meta for lists only).
- Error: `{ "error": { "code": "NOT_FOUND", "message": "...", "details": [...] } }`.
- Status codes: 200, 201, 400 validation, 404, 409 invalid state transition, 500.
- No login in the MVP: approving and rejecting take `reviewerName` in the body, stored as `approved_by`.

## 6. Understand: reasons and channels

### Reason taxonomy → next-best action

| Reason code | Evidence or typical phrasing | Next-best action |
|---|---|---|
| `affordability` | "money hard", "can't buy the big bundle" · weak evidence: trading down to cheaper bundles | Eligible lower-cost bundle / commercial intervention |
| `network_quality` | Evidence: decline overlaps a network incident in the customer's region · "no network", "data too slow" | Route to network/service team |
| `reduced_need` | "I don't use data much now", "got Wi-Fi at work" | **No incentive**; monitor |
| `competitor` | "using other network now", "their bundle cheaper" | Eligible retention/competitive intervention |
| `activation_difficulty` | Evidence: rising failed activations · "can't buy bundle", "USSD code not working" | Education / activation instructions |
| `unknown` | No evidence, no reply, low confidence, or a reason outside the list | Collect more evidence or human review |

Reason IDs match the frontend (`frontend/data/reason-taxonomy.json`) and are stored in the `reasons` table.

### Channels

All channels are **Orange's existing channels**. Resolve AI does not send messages, place calls or build a communication platform. Its boundary with a channel is:

```
Resolve AI: create feedback request ──hand off──▶ Orange channel contacts customer
Resolve AI: ingest + classify reply  ◀──returns── Orange channel collects reply
```

In the MVP, the Orange side is **simulated** (`/simulation/...`). In production it would be an adapter or export to Orange's systems.

| Channel (Orange-owned) | How feedback arrives | Stored as |
|---|---|---|
| `voice_call` | Orange calls on request | Call transcript |
| `sms` | Orange SMS on request | Message reply |
| `ussd` | Orange USSD prompt on request | Menu choice + optional short text |
| `field_agent_interview` | Orange field agent on request | Agent's interview notes |
| `customer_service` | Existing interactions (no request) | Ticket/interaction text |
| `facebook_comment` | Public comments (no request) | Comment text; linked to a customer only when identifiable, otherwise counted at region/segment level. Real use requires validated access and permissions |

The channel list lives in config so more channels can be added without schema changes.

### AI classification output (validated with Zod)

`{ reasonCode, confidence (0–1), sentiment (negative | neutral | positive), summary (formal, one sentence), keyPhrases[] }`. Confidence < 0.6 → `needs_review = true`.

## 7. Data model

Implemented in F1. Full diagram and the v1 → v2 mapping are in [`docs/erd.md`](erd.md); the code source of truth is `backend/src/db/schema/`.

A **case** (one detection episode for a customer) is the central record, matching the frontend's case-based workflow. It replaces the v1 `BEHAVIORAL_ASSESSMENT` and `ENGAGEMENT_SIGNAL` entities.

| Area | Tables |
|---|---|
| Catalog | `reasons`, `bundles` (USD/LRD), `actions` (next-best-action library with eligibility rules), `action_reasons`, `campaign_history` (synthetic recovery rates) |
| Detect inputs | `customers` (`LR-20417` style IDs, value tier, masked MSISDN), `bundle_activations` (one row per purchase, success/failed, currency), `network_faults` (customer reports and regional incidents) |
| Detect | `detection_runs`, `customer_metrics` (per run × customer × period: baseline/current/post-intervention), `cases` (priority score, contributions, queue status) |
| Understand | `feedback_requests` (handed off to Orange channels), `customer_feedback`, `reason_classifications` (reason, confidence, alternatives, evidence, source, human review) |
| Recommend / Act / Measure | `recommendations` (chosen action, eligibility checks, alternatives considered), `interventions` (`INT-4100` style references), `outcomes` (treated cases + matched control cohort) |
| Copilot (F10) | `ai_conversations`, added with its own migration in F10 |

Conventions: readable text keys where the UI shows them (`LR-20417`, `daily_mini_600`, `RUN-…`, `INT-…`); `uuid` elsewhere; fixed sets as Postgres enums; channels as config-validated text; timestamps `timestamptz`.

### Synthetic scenarios (F2)

| Scenario | Behavior | Reason path → action |
|---|---|---|
| **Hero (LR-20417)** | 18 → 6 bundles/month (−67%) | No evidence → Orange SMS → `affordability` → lower-cost bundle |
| Activation trouble | Rising failed activations | **Evidence** → `activation_difficulty` → activation instructions |
| Network outage | Decline during a regional incident | **Evidence** → `network_quality` → route to network team |
| Competitor | Sharp stop | No evidence → Orange voice call → `competitor` → retention offer |
| Reduced need | Gradual decline | No evidence → Orange USSD → `reduced_need` → no incentive |
| Silent | Decline, no reply | `no_response` → `unknown` → field agent interview / human review |
| Healthy / growing | Stable or rising | No action |

### Priority score v1 (F3)

Same formula as the frontend (`frontend/lib/analytics.ts`), so the numbers on screen don't change when the UI switches to the API. Five visible contributions, each capped:

| Contribution | Points |
|---|---|
| Usage drop vs own baseline | `min(40, round(drop% × 0.58))` |
| Value tier | high 18 · medium 10 · low 4 |
| Tenure | `min(15, round(months / 3))` |
| Days inactive | `min(12, round(days / 2.2))` |
| Recent care contacts (30 days) | `min(8, contacts × 3)` |

Bands: `high` ≥ 75, `medium` ≥ 55, otherwise `low`. All values live in `config/rules.ts`.

### Outcome rule v1 (F8)

Share of the original drop recovered, by activations and active days: ≥ 50% → `re_engaged`; 15–50% → `partially_engaged`; −10% to 15% → `no_change`; worse → `declined_further`.

## 9. Git workflow

- `main` always runs. Work on `feat/backend-<feature>` branches and merge through PRs.
- Conventional Commits with scopes: `feat(db): ...`, `feat(detect): ...`, `feat(understand): ...`, `docs(api): ...`, `chore: ...`.
- Small commits that each typecheck. Every PR has: summary, endpoints added, manual `curl` test steps.
- Never commit `.env`; keep `.env.example` current.

## 10. Definition of done (per feature)

- `npm run typecheck` and `npm run lint` pass.
- Endpoints documented in `docs/api-contract.md` with example responses.
- Manual test steps in the PR, run against the seeded Neon DB.
- Backend README updated if setup or scripts changed.
